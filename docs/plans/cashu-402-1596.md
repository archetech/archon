# Pay Drawbridge with ecash (#1596)

Status: plan for review.

Drawbridge's paywall answers an unpaid priced request with HTTP 402 and an L402
challenge, which only Lightning can pay. This plan adds
[NUT-24](https://github.com/cashubtc/nuts/blob/main/24.md), Cashu as an HTTP 402
payment method, as a second way to pay the same price. It also teaches Keymaster
to pay such a 402 from its own ecash, automatically, within a budget the operator
sets. An agent holding ecash can then call a priced Archon API with no Lightning
node, no channel and no account.

This is option A of [nut-november.md](nut-november.md).

## Decisions

Made on 2026-11-10:

- **Custody.** Drawbridge redeems each token through the node's own Keymaster
  (`receiveCashu`), so payments land in the node's existing, seed-recoverable Cashu
  wallet. Drawbridge holds no funds.
- **Mints.** Drawbridge accepts only the node's own mint, named by its public URL
  `<ARCHON_DRAWBRIDGE_PUBLIC_HOST>/cashu`, the URL `GET /cashu-mint` already
  publishes and `addCashu` already records. A node without an https public host
  has no such URL and offers Lightning only.
- **Paying.** Keymaster pays automatically, but only within limits the operator
  has set: a maximum per request and a total budget. Without them, it pays
  nothing.
- **Parity.** Full parity. Every phase ships in both Keymasters, the REST API,
  both SDKs, all three CLIs, MCP, the wallets and the standalone clients, as in
  [cashu-1058.md](cashu-1058.md).

## How a call is paid

1. Keymaster calls a priced Drawbridge route without payment.
2. Drawbridge answers 402. Alongside the existing `WWW-Authenticate: L402 …`
   challenge, it sends `X-Cashu: creqA…`, a NUT-18 payment request:
   - `a`: the operation's price in sats, as for L402;
   - `u`: `sat`;
   - `m`: the node's public mint URL.

   The body lists `acceptedMethods: ['lightning', 'cashu']` and includes the
   request. Each method is offered only when it can work: Lightning when the
   mediator is configured, Cashu when the node has a public mint and Drawbridge
   can reach the node's Keymaster.
3. Keymaster decodes the request, accepting both `creqA` and `creqB`, which
   NUT-24 requires of wallets. It pays only if all of these hold:
   - the mint is one of the paying identity's mints;
   - the amount is within the per-request maximum;
   - the amount is within the remaining budget.

   It then deducts the amount from the budget, makes the token with `sendCashu`,
   and retries the request with `X-Cashu: cashuB…`. The send is journaled like
   any other, so an unredeemed token can be reclaimed.
4. Drawbridge checks the token before doing any work. A token from a mint not in
   `m`, of another unit, for less than the price, or carrying spending conditions
   gets `400`, as NUT-24 specifies.
5. Drawbridge redeems the token with `KeymasterClient.receiveCashu(token, <node
   ID>)` against the node's Keymaster. Only once the swap succeeds does it serve
   the request. A token already spent gets `400`; a Keymaster or mint that cannot
   be reached gets `503`.
6. Drawbridge records a payment with `method: 'cashu'` next to the Lightning
   ones, and the payer's wallet settles the send on its next `cashu-check`.

A Cashu payment covers the request it comes with and nothing else, like a priced
L402 macaroon with one use. It issues no macaroon.

## Pieces

| Piece | Change |
|---|---|
| Drawbridge | `X-Cashu` challenge and verification in the L402 middleware; redemption through `@didcid/clients`' `KeymasterClient`; payment records with a method; `/capabilities` and docs |
| Compose | `ARCHON_DRAWBRIDGE_KEYMASTER_URL` (`http://keymaster:4226`) and an explicit `ARCHON_DRAWBRIDGE_KEYMASTER_ADMIN_KEY` passed alongside it. Per AGENTS.md, the local admin secret is not forwarded to a configurable URL implicitly |
| Keymaster (TS and Python) | a 402 handler on the Gatekeeper client that consults a payer; the payer checks the limits, records the deduction and calls `sendCashu`; `setCashuAutopay`, `getCashuAutopay` and a list of autopay payments |
| REST, SDKs, CLIs | routes, client methods and commands for the autopay settings and payments, in both ports |
| MCP | tools for the settings and payments. Setting the limits is marked mutating, since it authorises spending |
| UIs | the limits and the payments made, in the Cashu view of the wallets and the standalone clients |

The limits live in the wallet, per identity, next to its mints. The remaining
budget is written down before the token is made, so a crash cannot overspend it;
a payment that fails before sending restores it.

## Testing

- **Drawbridge:** unit tests with a fake Keymaster cover the challenge, each
  `400` case, a spent token, and Keymaster unavailable. A test against a real
  `cashubtc/mintd` with fakewallet covers the full redeem.
- **Keymaster:** both ports run against shared fixtures for payment requests and
  limits. Each port is driven against real mintd and a paywalled Drawbridge, as
  AGENTS.md requires for Cashu changes.
- **End to end:** `tests/cashu-regtest` gains a scenario: a paywalled Drawbridge,
  with an agent paying for `createDID` with ecash, under both Keymasters.

## Known limits

- **A failed request is still paid.** Drawbridge redeems before serving, so a
  request that then fails with a `5xx` has already been paid for. L402 does not
  count such a use; a Cashu payment cannot be taken back.
- **Overpayment is kept.** NUT-24 accepts any token of at least the price.
  Keymaster sends the exact amount, but other wallets may send more.
- **Clients covered.** Only Keymaster's Gatekeeper client pays. Other callers of
  priced routes see the 402 as before.

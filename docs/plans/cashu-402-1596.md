# Pay Drawbridge with ecash (#1596)

Status: plan for review.

Drawbridge's paywall answers an unpaid priced request with HTTP 402 and an L402
challenge, which only Lightning can pay. This plan adds
[NUT-24](https://github.com/cashubtc/nuts/blob/main/24.md), Cashu as an HTTP 402
payment method, as a second way to pay the same price. It also teaches Keymaster
to pay such a 402 from its own ecash, automatically, within a budget the operator
sets. An agent holding ecash can then call a priced Archon API with no Lightning
node, no channel and no account.

This is option A of [nut-november.md](nut-november.md).

## Decisions

Made on 2026-11-10:

- **Custody.** Drawbridge redeems each token through the node's own Keymaster
  (`receiveCashu`), so payments land in the node's existing, seed-recoverable Cashu
  wallet. Drawbridge holds no funds.
- **Mints.** Drawbridge accepts only the node's own mint, named by its public URL
  `<ARCHON_DRAWBRIDGE_PUBLIC_HOST>/cashu`, the URL `GET /cashu-mint` already
  publishes and `addCashu` already records. A node without an https public host
  has no such URL and offers Lightning only.
- **Paying.** Keymaster pays automatically, but only within limits the operator
  has set: a maximum per request and a total budget. Without them, it pays
  nothing.
- **Parity.** Full parity. Every phase ships in both Keymasters, the REST API,
  both SDKs, all three CLIs, MCP, the wallets and the standalone clients, as in
  [cashu-1058.md](cashu-1058.md).

## How a call is paid

1. Keymaster calls a priced Drawbridge route without payment.
2. Drawbridge answers 402. Alongside the existing `WWW-Authenticate: L402 …`
   challenge, it sends `X-Cashu: creqA…`, a NUT-18 payment request:
   - `a`: the operation's price in sats, as for L402;
   - `u`: `sat`;
   - `m`: the node's public mint URL.

   The body lists `acceptedMethods: ['lightning', 'cashu']` and includes the
   request. Each method is offered only when it can work: Lightning when the
   mediator answers, Cashu while the identity `ARCHON_NODE_ID` on the node's
   Keymaster holds the node mint. That needs operator setup: run
   `add-cashu <node ID>` once. Drawbridge checks it before offering Cashu.
3. Keymaster decodes the request, accepting both `creqA` and `creqB`, which
   NUT-24 requires of wallets. The amount asked is net of the receiver's fee,
   and `sendCashu` grosses the token up to cover that fee, then pays its own
   swap fees too. So the limits apply to the whole debit from the wallet, not
   the price. Keymaster pays only if all of these hold:
   - the mint is one of the paying identity's mints;
   - the full debit, estimated before sending, is within the per-request maximum;
   - it is within the remaining budget.

   **Payment happens outside the operation.** The Gatekeeper client does not
   pay in the middle of a call. It turns the 402 into a payment-required error
   that carries the request, and the Keymaster operation fails as it would on
   any Gatekeeper error, releasing the wallet lock. Autopay wraps the public
   operation: it catches that error, pays, and runs the whole operation again.
   The rerun's request to the same route carries `X-Cashu: cashuB…`. Paying
   needs the wallet lock (`sendCashu` takes it), so paying from inside an
   operation that holds it, as `createId` does around `createDID`, would
   deadlock. Paying after the operation has let go of the lock avoids that
   without changing how any operation locks the wallet.

   Only the outermost Keymaster call pays. Operations call one another, such as
   `rotateKeys` calling `updateDID` while it holds the lock, so a nested call
   passes the error up unpaid, and the one invocation it belongs to counts its
   writes. Each port carries that invocation in its async context
   (`AsyncLocalStorage`, `contextvars`).

   It reserves that debit against the budget and makes the token with
   `sendCashu`. Once the send is recorded, the reservation settles to what
   actually left the wallet, and any difference returns to the budget. The
   send is journaled like any other, so a token the rerun never uses can be
   reclaimed.

   **Reservations follow the send journal.** Each reservation is stored in the
   wallet with a link to its send operation, so it survives restarts. A
   `sendCashu` that fails with an unclear outcome, such as a lost mint
   response, can still have sent: both ports have tests where recovery later
   records such a send as outstanding. So the reservation is kept, not
   released, until `cashu-check` recovery establishes the debit. It then
   settles to what was recorded, or is released only when recovery shows
   nothing left the wallet.

   **Only operations safe to rerun are paid.** Paying means running the
   operation a second time, so autopay pays only when the 402 came from the
   operation's first Gatekeeper write. Nothing has been published yet, and a
   failed wallet mutation is discarded, so the rerun starts from the same
   state: a refused `createId` leaves the counter where it was. A 402 on a
   later write, after an earlier one went through, is returned to the caller
   unpaid, since a rerun would repeat that earlier write. So is a 402 on a
   request whose body is a one-shot stream, such as `addDataStream`'s
   `POST /ipfs/stream`, which cannot be sent again. Such a caller pays and
   retries itself, or pays with an L402 credential.
4. Drawbridge checks the token before doing any work. A token from a mint not in
   `m`, of another unit, for less than the price, or carrying spending conditions
   gets `400`, as NUT-24 specifies.
5. Drawbridge redeems the token with `KeymasterClient.receiveCashu(token, <node
   ID>)` against the node's Keymaster.
   - A token already spent gets `400`; a Keymaster or mint that cannot be
     reached gets `503`.
   - A successful redemption can bring in less than the face value: proofs
     already spent are skipped, and the mint takes its fee. So the amount
     received must cover the price before the request is served. A token that
     brings in less gets `400`, and what it brought in stays received.

   `X-Cashu` is redacted from Drawbridge's request logs, since a token refused
   before redemption is still spendable.
6. Drawbridge records a payment with `method: 'cashu'` next to the Lightning
   ones, and the payer's wallet settles the send on its next `cashu-check`.

A Cashu payment covers the request it comes with and nothing else, like a priced
L402 macaroon with one use. It issues no macaroon.

## Pieces

| Piece | Change |
|---|---|
| Drawbridge | `X-Cashu` challenge and verification in the L402 middleware; redemption through `@didcid/clients`' `KeymasterClient`; payment records with a method; `/capabilities` and docs |
| Compose | `ARCHON_DRAWBRIDGE_KEYMASTER_URL` (`http://keymaster:4226`) and an explicit `ARCHON_DRAWBRIDGE_KEYMASTER_ADMIN_KEY` passed alongside it. Per AGENTS.md, the local admin secret is not forwarded to a configurable URL implicitly |
| Keymaster (TS and Python) | a payment-required error from the Gatekeeper client; an autopay wrapper around public operations that checks the limits, records the deduction, calls `sendCashu` and reruns the operation with the token; `setCashuAutopay`, `getCashuAutopay` and a list of autopay payments |
| REST, SDKs, CLIs | routes, client methods and commands for the autopay settings and payments, in both ports |
| MCP | tools for the settings and payments. Setting the limits is marked mutating, since it authorises spending |
| UIs | the limits and the payments made, in the Cashu view of the wallets and the standalone clients |

The limits live in the wallet, per identity, next to its mints. The remaining
budget is written down before the token is made, so a crash cannot overspend it;
a payment that fails before sending restores it.

## Testing

- **Drawbridge:** unit tests with a fake Keymaster cover the challenge, each
  `400` case, a spent token, a partly spent token that brings in less than the
  price, Keymaster unavailable, and log redaction. A test against a real
  `cashubtc/mintd` with fakewallet covers the full redeem.
- **Keymaster:** both ports run against shared fixtures for payment requests and
  limits. They include a fee-bearing mint, where the debit exceeds the price,
  and a priced `createId`. Further cases:
  - an unclear send whose reservation survives a restart and settles on
    recovery;
  - a streamed upload that gets its 402 with nothing spent;
  - a 402 on a second write, returned unpaid with the first write not
    repeated, including one made by a nested call such as `createFile`'s
    `createAsset`;
  - a priced `rotateKeys`, whose nested `updateDID` gets the 402 under the
    wallet lock and is paid only after `rotateKeys` returns;
  - a rerun that does not use its token, which `cashu-check` reclaims.

  Each port is driven against real mintd and a paywalled Drawbridge, as
  AGENTS.md requires for Cashu changes.
- **End to end:** `tests/cashu-regtest` gains a scenario: a paywalled Drawbridge,
  with an agent paying for `createDID` with ecash, under both Keymasters.

## Known limits

- **A failed request is still paid.** Drawbridge redeems before serving, so a
  request that then fails with a `5xx` has already been paid for. L402 does not
  count such a use; a Cashu payment cannot be taken back.
- **Overpayment is kept.** NUT-24 accepts any token whose redemption covers the
  price. Keymaster's token can exceed the price by the fee gross-up when no
  exact gross exists, and other wallets may send more.
- **Clients covered.** Only Keymaster's operations pay, and only when the 402
  came from their first Gatekeeper write. Streamed uploads, later writes and
  other callers of priced routes see the 402 as before.

# Pay Drawbridge with ecash (#1596)

Status: plan for review.

Drawbridge's paywall answers an unpaid priced request with HTTP 402 and an L402
challenge, which only Lightning can pay. This plan adds
[NUT-24](https://github.com/cashubtc/nuts/blob/main/24.md), Cashu as an HTTP 402
payment method, as a second way to pay the same price. It also gives Keymaster
a command that pays a Cashu payment request from its own ecash. An agent holding
ecash can then call a priced Archon API with no Lightning node, no channel and
no account.

This is option A of [nut-november.md](nut-november.md).

## Decisions

Made on 2026-11-10:

- **Custody.** Drawbridge redeems each token through the node's own Keymaster
  (`receiveCashu`), so payments land in the node's existing, seed-recoverable Cashu
  wallet. Drawbridge holds no funds.
- **Mints.** Drawbridge accepts only the node's own mint, named by its public URL
  `<ARCHON_DRAWBRIDGE_PUBLIC_HOST>/cashu`, the URL `GET /cashu-mint` already
  publishes and `addCashu` already records. A node without an https public host
  has no such URL and offers Lightning only.
- **Parity.** Full parity. Every phase ships in both Keymasters, the REST API,
  both SDKs, all three CLIs, MCP, the wallets and the standalone clients, as in
  [cashu-1058.md](cashu-1058.md).

Revised on 2026-11-11:

- **Paying.** The caller pays. Keymaster gets a command that turns a Cashu
  payment request into a token, and whoever made the HTTP request sends it
  again with that token. Keymaster does not pay 402s on its own Gatekeeper
  calls; see [Automatic payment](#automatic-payment) for why.

## How a call is paid

1. A client calls a priced Drawbridge route without payment.
2. Drawbridge answers 402. Alongside the existing `WWW-Authenticate: L402 …`
   challenge, it sends `X-Cashu: creqA…`, a NUT-18 payment request:
   - `a`: the operation's price in sats, as for L402;
   - `u`: `sat`;
   - `m`: the node's public mint URL.

   The body lists `acceptedMethods: ['lightning', 'cashu']` and includes the
   request. Each method is offered only when it can work: Lightning when the
   mediator answers, Cashu while the identity `ARCHON_NODE_ID` on the node's
   Keymaster holds the node mint. That needs operator setup: run
   `add-cashu <node ID>` once. Drawbridge checks it before offering Cashu.
3. The client hands the request to its Keymaster: `payCashuRequest(request)`,
   `cashu-pay-request` on the CLIs. Keymaster decodes it, accepting both `creqA`
   and `creqB`, which NUT-24 requires of wallets, and refuses a request that is
   not in sats, names no amount, names no mint the paying identity holds, or
   asks for a locked token (`nut10`), which `sendCashu` does not make.
   A caller can pass a maximum, above which Keymaster refuses to pay. It then
   makes the token with `sendCashu`. The amount asked is net of the receiver's
   fee, and `sendCashu` grosses the token up to cover it, so the debit can
   exceed the price; the result reports the amount, the fee and the send's
   operation ID. The send is journaled like any other, so a token that is
   never redeemed can be reclaimed.

   The client then repeats its request with `X-Cashu: cashuB…`.
4. Drawbridge checks the token before doing any work. A token from a mint not in
   `m`, of another unit, for less than the price, or carrying spending conditions
   gets `400`, as NUT-24 specifies.
5. Drawbridge redeems the token with `KeymasterClient.receiveCashu(token, <node
   ID>)` against the node's Keymaster.
   - A token already spent gets `400`; a Keymaster or mint that cannot be
     reached gets `503`.
   - A successful redemption can bring in less than the face value: proofs
     already spent are skipped, and the mint takes its fee. So the amount
     received must cover the price before the request is served. A token that
     brings in less gets `400`, and what it brought in stays received.

   `X-Cashu` is redacted from Drawbridge's request logs, since a token refused
   before redemption is still spendable.
6. Drawbridge records a payment with `method: 'cashu'` next to the Lightning
   ones, and the payer's wallet settles the send on its next `cashu-check`.

A Cashu payment covers the request it comes with and nothing else, like a priced
L402 macaroon with one use. It issues no macaroon.

## Pieces

| Piece | Change |
|---|---|
| Drawbridge | `X-Cashu` challenge and verification in the L402 middleware; redemption through `@didcid/clients`' `KeymasterClient`; payment records with a method; `/capabilities` and docs |
| Compose | `ARCHON_DRAWBRIDGE_KEYMASTER_URL` (`http://keymaster:4226`) and an explicit `ARCHON_DRAWBRIDGE_KEYMASTER_ADMIN_KEY` passed alongside it. Per AGENTS.md, the local admin secret is not forwarded to a configurable URL implicitly |
| Keymaster (TS and Python) | `payCashuRequest`: decode a NUT-18 request, check it, and make the token with `sendCashu` |
| REST, SDKs, CLIs | a route, client methods and `cashu-pay-request`, in both ports |
| MCP | a tool for it, marked mutating, since it spends |
| UIs | a field in the Cashu view of the wallets and the standalone clients that takes a payment request and returns the token |

## Testing

- **Drawbridge:** unit tests with a fake Keymaster cover the challenge, each
  `400` case, a spent token, a partly spent token that brings in less than the
  price, Keymaster unavailable, and log redaction. A test against a real
  `cashubtc/mintd` with fakewallet covers the full redeem.
- **Keymaster:** both ports run against shared fixtures of payment requests:
  `creqA` and `creqB`, a wrong unit, no amount, a mint the identity does not
  hold, a `nut10` condition, an amount over the caller's maximum, and a fee-bearing mint, where the
  debit exceeds the price. Each port is driven against real mintd and a
  paywalled Drawbridge, as AGENTS.md requires for Cashu changes.
- **End to end:** `tests/cashu-regtest` gains a scenario: a paywalled Drawbridge,
  with an agent paying for `createDID` with ecash, under both Keymasters.

## Automatic payment

Not in this plan. Keymaster's own Gatekeeper calls through a paywalled
Drawbridge get the 402 as they do today, with Lightning or with ecash.

Paying such a 402 automatically was planned and dropped. `sendCashu` takes the
wallet's mutation lock, and operations such as `createId` hold that lock while
they call Gatekeeper, so a payment made at that point deadlocks. Two ways
around it were tried:

- Calling Gatekeeper outside the lock (#1602, closed). Every other wallet
  operation can then land in the gap, and each needed its own check in core
  identity code.
- Failing the operation, paying, and running it again. An operation with two
  priced writes, such as `backupId`, never finishes: each run pays for the
  first write and fails on the second. It also needs async context that
  browsers lack, and the wallets run Keymaster in the page.

A design that works has to pay at the moment of the 402 without the wallet
lock, for example from ecash set aside beforehand. That is a second way of
spending beside the send journal, and is left for a later plan.

## Known limits

- **A failed request is still paid.** Drawbridge redeems before serving, so a
  request that then fails with a `5xx` has already been paid for. L402 does not
  count such a use; a Cashu payment cannot be taken back.
- **Overpayment is kept.** NUT-24 accepts any token whose redemption covers the
  price. Keymaster's token can exceed the price by the fee gross-up when no
  exact gross exists, and other wallets may send more.
- **Clients covered.** A client pays its own HTTP requests. Keymaster's
  Gatekeeper calls are not paid; see [Automatic payment](#automatic-payment).
